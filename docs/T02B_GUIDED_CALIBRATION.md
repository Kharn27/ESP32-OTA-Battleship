# T02-B / Issue #21 — guided CYD touchscreen calibration (Phase A)

## Mission boundary / identity

**Independent calibration mode**, not a battle/deployment application. T02-B
collects raw XPT2046 measurements for PO/Pilotage. It does **not** update
D09's provisional touch transform, B01 debounce dispatcher, NVS, gameplay,
board configuration, panel MADCTL or other repositories. Phase B is a
separate reviewed decision after PO data have been received.

Development base: `main` at `0642e7abc1d4285d978586042df66edcbff5b4ec`.
Branch: `spike/issue-21-t02b-guided-calibration`.
The final HEAD, ESP32 firmware SHA-256 and CI run must be attached to the PR
**after the CI has produced them**. Do not infer the firmware SHA from a commit
SHA or from a former D09 binary.

## Hardware and boot

One classic ESP32-2432S028R (ILI9341 320x240, XPT2046), ESP-IDF v5.5.6,
target `esp32`. No PSRAM or microSD. Reuse the existing WARSHIP
`warship_lcd` and `warship_touch` drivers; SPI2 LCD profile console
**case 10**, SPI3 XPT2046 and IRQ GPIO36, one runtime task owns each bus.
The 320x240 RGB565 frame is generated into the **existing 5120-byte DMA
band** (8 rows, 30 serialized bands per complete screen); no framebuffer.
The screen is updated only after an accepted gesture or control transition.
Text/crosshairs are technical assets generated by a pure C99 renderer.

Kconfig: `CYD WARSHIP boot mode → T02-B guided five-point raw calibration`.
The branch has `sdkconfig.defaults` with
`CONFIG_WARSHIP_BOOT_T02_CAL=y` so its CI firmware boots calibration.
This **branch-local default** must be reconsidered by Pilotage before merge
and on eventual Phase B; the ordinary Kconfig choice default remains D09.
Ensure there is no pre-existing `sdkconfig` overriding this option.

With a local ESP-IDF v5.5.6 checkout:

```sh
git rev-parse HEAD
idf.py --version
idf.py set-target esp32
idf.py menuconfig      # verify EXACTLY T02-B calibration mode
idf.py build
idf.py size
idf.py size-components
sha256sum build/cyd_warship.bin
idf.py -p /dev/ttyUSB0 flash monitor
```

**Do not flash until Pilotage has reviewed/approved the exact HEAD.**
For CI artifacts, verify `cyd_warship.bin` SHA-256 and use the matching
`flasher_args.json`, bootloader and partition table. Do not guess
application offsets and **never run erase-flash**; protect any pre-existing
palmarès NVS, checking the partition layout before flashing. If the local
SDK build or mode differs from CI, record its own hash and do not mislabel it.

## PO physical protocol — one board

Record board revision, USB connector, serial port, tool version, boot commit
and actual flashed BIN SHA-256. Capture UART from reset through completion.
Photograph the complete screen with all four corners visible.

1. BOOT: record `BOOT_MODE=T02_CAL` and
   `LCD_PROFILE_PASS case=10`, verify full 320x240 screen and no pixels
   left from an old firmware; if not, STOP and report photograph + logs.
2. Cible **HAUT GAUCHE**, screen (24,24): gently press the crosshair with
   the stylus and release completely; repeat three times. Confirm
   `CAL_ACCEPT point=1 press=1/2/3` separately, `CAL_SPREAD` and
   `MEASURED TAP NEXT` text. No screen hitbox is used.
3. To confirm the point, perform one separate short tap ANYWHERE; screen
   advances to **HAUT DROIT** (296,24). Repeat the 3 presses.
4. Similarly record **CENTRE** (160,120), **BAS GAUCHE** (24,216) and
   **BAS DROIT** (296,216), always three separate presses with a clear
   release and a separate short confirmation tap after the third.
   This is a minimum of **15 raw measurements + 5 confirmation taps**.
5. To retry the CURRENT target before confirming it, hold the stylus
   down continuously at any position for at least 2200 ms; `CAL_RETRY`
   clears only that target's three recorded presses. Release fully
   before attempting again. A hold on the final DONE view restarts all.
6. Verify rejection of a quick tap shorter than 40 ms when feasible,
   short release bounces and any reported SPI or saturated ADC values.
   Do not force touches on unreliable edges and do not interpret a single
   touch/release as two accepted measurements.
7. Final review: screen says DONE SEE UART. Save all
   `CAL_POINT`, `CAL_RAW` (15 entries), `CAL_SPREAD`,
   `CAL_PROPOSAL NOT_APPLIED`, `MEM`, `DRAW`,
   `TOUCH_SPI_ERROR` and `CAL_EVENT` logs.
   Cold reboot and repeat at least one target, noting the boot SHA.

Press requirements: stable contact >=40 ms, stable continuous release
>=80 ms. The sample's median is generated from three XPT2046 readings
PER CHANNEL by the existing driver. **One accepted measurement is still
one distinct pen-down/pen-up gesture**. At 20 ms polling, aim for
deliberate taps of ~150–300 ms rather than the exact 40 ms threshold.

## Report and interpretation

The raw touch axes are NEVER normalized to button hitboxes during Phase A.
For each target, the firmware stores three independent raw (X,Y) pairs
and reports their median and max-min dispersion along each raw axis.
Two candidate assignments (direct and swapped) are compared by
pixel reprojection error using all five median pairs. Endpoint values are
linear extrapolations from the physical four corners (24 px margins),
clamped to 0..4095. Positive/negative endpoint order is the axis sense.

`CAL_PROPOSAL NOT_APPLIED` reports `swap,x0,x1,y0,y1,max_err_px,sum_sq_px`.
The error is measured **at the five sampled targets only**, not a
whole-screen accuracy guarantee. If axes are degenerate or indistinguishable,
the firmware reports `UNDETERMINED` and requests additional measurements.
Large dispersion or residual error also demands Pilotage review; the code
never silently declares the panel calibrated.

The reference from DoomRPG-RE is used **only for comparison**:
Raw X 372..3800, Raw Y 331..3802; screen X from Raw Y,
screen Y from Raw X. With these *hypothetical* values a previously logged
D09 press raw=(2092,3346) projects near (277,120), but the new constants
must follow actual CYD measurements. No Arduino/C++ or GPL source copied.

## Status evidence

  acquisition, bounces, invalid ADC/SPI, redo/restart, normal/swapped/
